## Vì sao phải bắt đầu từ API?

Hầu hết sản phẩm AI hiện nay — chatbot chăm sóc khách hàng, trợ giảng, công cụ tóm tắt tài liệu, agent tự động hoá — đều được xây trên cùng một viên gạch: **gửi một request tới LLM API và xử lý phản hồi**. Làm việc trực tiếp với API (thay vì chỉ dùng giao diện chat) giúp bạn:

- **Kiểm soát** chính xác model nào được gọi, với tham số nào, ngữ cảnh nào
- **Đo lường** được độ trễ, số token và chi phí — những con số quyết định sản phẩm có sống được hay không
- **Tự động hoá**: gọi model hàng nghìn lần trong một pipeline, không cần người ngồi gõ

# LLM hoạt động như thế nào?

## Large Language Model là gì?

**LLM (Large Language Model)** là một mạng nơ-ron rất lớn — thường dựa trên kiến trúc **Transformer** — được huấn luyện trên lượng văn bản khổng lồ để làm đúng một việc: **dự đoán token tiếp theo** dựa trên chuỗi token phía trước.

Nghe đơn giản, nhưng khi mô hình đủ lớn và dữ liệu đủ nhiều, khả năng "đoán tiếp" này sinh ra những năng lực nổi bật: trả lời câu hỏi, dịch, tóm tắt, viết code, suy luận nhiều bước.

## Token — đơn vị cơ bản của LLM

Model không đọc từng chữ cái hay từng từ, mà đọc **token** — các mảnh văn bản do bộ tách từ (tokenizer) tạo ra. Một token có thể là một từ, một phần của từ, một dấu câu hoặc một khoảng trắng.

~~~text
"Hello world"          → ["Hello", " world"]                 (2 token)
"tokenization"         → ["token", "ization"]                (2 token)
"Xin chào các bạn"     → ["X", "in", " ch", "ào", " các", " bạn"]  (có thể 5–7 token tuỳ tokenizer)
~~~

Một vài quy tắc ước lượng:

- Tiếng Anh: trung bình **1 token ≈ 4 ký tự ≈ 0,75 từ**
- Tiếng Việt có dấu: thường tốn **nhiều token hơn** cho cùng một ý, vì tokenizer được huấn luyện chủ yếu trên tiếng Anh và các ký tự có dấu hay bị tách nhỏ
- Code, JSON, URL dài và chuỗi số cũng tốn nhiều token

> **Vì sao token quan trọng?** Vì mọi giới hạn và chi phí của LLM đều tính bằng token: context window, `max_tokens`, giá tiền mỗi request, và cả tốc độ sinh (token/giây).

## Next-token prediction — model "suy nghĩ" ra sao

Khi sinh câu trả lời, model lặp lại quy trình sau cho đến khi gặp token kết thúc hoặc chạm giới hạn độ dài:

1. Nhận toàn bộ chuỗi token hiện có (prompt + phần đã sinh)
2. Tính **phân phối xác suất** cho mọi token trong bộ từ vựng (thường 100.000–200.000 token)
3. **Chọn** một token từ phân phối đó (cách chọn phụ thuộc `temperature`, `top_p`)
4. Nối token vừa chọn vào chuỗi và quay lại bước 1

~~~text
Prompt:  "Thủ đô của Việt Nam là"
Bước 1 → " Hà"   (xác suất 0.92)
Bước 2 → " Nội"  (xác suất 0.98)
Bước 3 → "."     (xác suất 0.71)
Bước 4 → <kết thúc>
~~~

Hệ quả quan trọng: model sinh **từng token một**, nên câu trả lời càng dài thì càng chậm và càng tốn tiền. Đây cũng là lý do streaming (hiển thị từng phần) giúp trải nghiệm tốt hơn nhiều.

## Transformer và self-attention (ở mức trực giác)

Trước 2017, các mô hình ngôn ngữ (RNN, LSTM) đọc văn bản tuần tự từng từ, khó nhớ các phụ thuộc xa và khó huấn luyện song song. Kiến trúc **Transformer** (bài báo *Attention Is All You Need*, 2017) thay đổi điều này bằng cơ chế **self-attention**: mỗi token được "nhìn" tới mọi token khác trong chuỗi và tự quyết định nên chú ý tới token nào nhiều hơn.

Ví dụ trong câu *"Con mèo không ăn cá vì **nó** đã no"*, self-attention giúp model liên kết "nó" với "con mèo" chứ không phải "cá".

## LLM được tạo ra qua những giai đoạn nào?

| Giai đoạn | Dữ liệu | Kết quả |
| --- | --- | --- |
| **Pre-training** | Hàng nghìn tỷ token văn bản từ internet, sách, code | Mô hình nền (base model) biết "đoán tiếp" văn bản |
| **Instruction tuning (SFT)** | Các cặp chỉ dẫn → câu trả lời mẫu do con người viết | Mô hình biết làm theo yêu cầu |
| **Alignment (RLHF / DPO…)** | Đánh giá, xếp hạng câu trả lời của con người | Câu trả lời hữu ích, an toàn, đúng mực hơn |

## Context window — bộ nhớ làm việc

**Context window** là tổng số token tối đa model xử lý được trong một lần gọi, **bao gồm cả input và output**. Mọi thứ bạn muốn model "biết" trong lượt đó — system prompt, lịch sử hội thoại, tài liệu đính kèm, câu hỏi — đều phải nằm trong cửa sổ này.

- Model **không có trí nhớ giữa các request**. "Nhớ hội thoại" thực chất là ứng dụng gửi lại lịch sử trong mỗi request.
- Context càng dài thì càng tốn tiền, càng chậm, và model có thể "bỏ sót" thông tin nằm ở giữa đoạn dài.

## Giới hạn bẩm sinh của LLM

- **Hallucination (ảo giác):** model có thể tạo ra thông tin sai nhưng nghe rất thuyết phục, vì nó tối ưu cho việc sinh văn bản hợp lý chứ không phải kiểm chứng sự thật.
- **Kiến thức bị đóng băng** tại thời điểm cắt dữ liệu huấn luyện (knowledge cutoff).
- **Không biết dữ liệu riêng** của bạn: tài liệu nội bộ, bài giảng của khoá học…
- **Tính toán chính xác kém** với số lớn, vì model xử lý số như token chứ không như phép tính.
- **Không tất định:** cùng prompt có thể cho câu trả lời khác nhau nếu `temperature > 0`.

# Gọi Chat Completions API và đo độ trễ

## Cấu trúc một request

Mỗi request tới Chat Completions API gồm ba phần chính:

1. **model** — tên model muốn dùng, ví dụ `gpt-4o-mini`
2. **messages** — danh sách tin nhắn theo thứ tự thời gian
3. **tham số sinh** — `temperature`, `max_tokens`… (xem phần tiếp theo)

Mỗi message có một `role`:

| Role | Ai viết | Dùng để làm gì |
| --- | --- | --- |
| `system` | Nhà phát triển | Đặt vai trò, phạm vi, quy tắc xuyên suốt cho model |
| `user` | Người dùng | Câu hỏi, yêu cầu |
| `assistant` | Model (các lượt trước) | Lịch sử câu trả lời để model giữ mạch hội thoại |

## Hello world

~~~python
from openai import OpenAI

client = OpenAI()  # tự đọc OPENAI_API_KEY và OPENAI_BASE_URL từ biến môi trường

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "Bạn là trợ giảng Python, trả lời ngắn gọn bằng tiếng Việt."},
        {"role": "user", "content": "List và tuple khác nhau thế nào?"},
    ],
)

print(resp.choices[0].message.content)
~~~

## Đọc hiểu response

~~~json
{
  "id": "chatcmpl-abc123",
  "model": "gpt-4o-mini-2024-07-18",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "List có thể thay đổi (mutable)..." },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 42, "completion_tokens": 118, "total_tokens": 160 }
}
~~~

Các trường cần quan tâm:

- `choices[0].message.content` — nội dung câu trả lời
- `finish_reason` — **vì sao model dừng**:
  - `stop`: model tự kết thúc câu trả lời — trường hợp bình thường
  - `length`: bị cắt vì chạm `max_tokens` hoặc hết context window — câu trả lời **không trọn vẹn**
  - `content_filter`: bị bộ lọc nội dung chặn
  - `tool_calls`: model muốn gọi một công cụ (sẽ học ở các buổi về agent)
- `usage` — số token thật của input (`prompt_tokens`) và output (`completion_tokens`), dùng để tính chi phí

> **Lỗi hay gặp:** chỉ đọc `content` mà bỏ qua `finish_reason`. Khi `finish_reason == "length"`, ứng dụng nên báo cho người dùng hoặc tăng `max_tokens`, thay vì hiển thị một câu trả lời cụt như thể nó hoàn chỉnh.

## Task 1.1 — Đo độ trễ

**Độ trễ (latency)** là thời gian từ lúc gửi request đến khi nhận đủ phản hồi. Dùng `time.perf_counter()` vì nó chính xác hơn `time.time()` cho việc đo khoảng thời gian.

~~~python
import time
from openai import OpenAI

client = OpenAI()

def call_model(prompt: str, model: str = "gpt-4o-mini", temperature: float = 0.2) -> dict:
    start = time.perf_counter()
    resp = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}],
        temperature=temperature,
    )
    latency = time.perf_counter() - start

    return {
        "text": resp.choices[0].message.content,
        "latency_s": round(latency, 3),
        "finish_reason": resp.choices[0].finish_reason,
        "input_tokens": resp.usage.prompt_tokens,
        "output_tokens": resp.usage.completion_tokens,
    }
~~~

## Độ trễ phụ thuộc vào những gì?

- **Kích thước model:** model lớn thường chậm hơn model nhỏ
- **Độ dài output:** mỗi token output phải sinh tuần tự — đây thường là yếu tố lớn nhất
- **Độ dài input:** ảnh hưởng ít hơn nhưng vẫn đáng kể với context rất dài
- **Tải của nhà cung cấp** và **khoảng cách mạng** — dao động theo giờ trong ngày

Vì độ trễ dao động, **đừng kết luận từ một lần đo**. Hãy đo nhiều lần và xem trung vị (median) cùng p95.

~~~python
import statistics

def benchmark(prompt: str, model: str, runs: int = 5) -> dict:
    latencies = [call_model(prompt, model)["latency_s"] for _ in range(runs)]
    return {
        "model": model,
        "median_s": statistics.median(latencies),
        "max_s": max(latencies),
    }
~~~

## Task 1.2 — Tái sử dụng cho model nhỏ hơn

Hàm `call_model` nhận `model` làm tham số, nên đổi sang model nhỏ chỉ là đổi một chuỗi. Đây là nguyên tắc thiết kế quan trọng: **không hard-code tên model** trong logic, hãy đưa vào tham số hoặc biến môi trường để dễ thay đổi khi giá cả hay chất lượng model thay đổi.

# Tham số sinh: temperature, top_p, max_tokens

## Nhắc lại: model chọn token như thế nào?

Ở mỗi bước, model tính xác suất cho mọi token có thể xuất hiện tiếp theo. Các tham số sinh quyết định **cách chọn** một token từ phân phối xác suất đó.

~~~text
Ngữ cảnh: "Hôm nay trời rất"
  " đẹp"   0.45
  " nắng"  0.25
  " lạnh"  0.15
  " mưa"   0.10
  ...      0.05
~~~

## temperature (thường từ 0 đến 2)

`temperature` "làm phẳng" hoặc "làm nhọn" phân phối xác suất trước khi chọn:

- **Gần 0:** phân phối rất nhọn → gần như luôn chọn token có xác suất cao nhất (" đẹp"). Kết quả **ổn định, lặp lại được**.
- **Khoảng 1:** giữ nguyên phân phối gốc → đa dạng vừa phải.
- **Lớn hơn 1:** phân phối phẳng → token hiếm cũng có cơ hội được chọn. Kết quả **sáng tạo nhưng dễ lan man, sai lệch**.

> `temperature = 0` **không đảm bảo** kết quả giống hệt 100% giữa các lần gọi (do tính toán song song trên GPU), nhưng là cách gần nhất để có kết quả ổn định.

## top_p (từ 0 đến 1) — nucleus sampling

`top_p` chỉ giữ lại **nhóm token nhỏ nhất có tổng xác suất tích luỹ ≥ top_p**, rồi chọn trong nhóm đó.

Với ví dụ trên và `top_p = 0.7`: giữ " đẹp" (0.45) + " nắng" (0.25) = 0.70 → chỉ chọn giữa hai token này, loại bỏ " lạnh", " mưa".

> **Khuyến nghị:** chỉ điều chỉnh **một trong hai** tham số `temperature` hoặc `top_p`, giữ tham số còn lại ở mặc định. Chỉnh cả hai cùng lúc khiến hành vi khó dự đoán.

## max_tokens — giới hạn độ dài output

- Giới hạn **số token output** tối đa model được sinh trong request này
- Đặt quá thấp → câu trả lời bị cắt giữa chừng, `finish_reason = "length"`
- Không đặt → model có thể sinh rất dài, **tốn tiền và chậm**
- Nên đặt theo nhu cầu thực tế: câu trả lời chat ngắn khoảng 300–800 token, tóm tắt tài liệu dài hơn

## Các tham số khác hay dùng

| Tham số | Tác dụng | Khi nào dùng |
| --- | --- | --- |
| `stop` | Danh sách chuỗi mà khi gặp thì model dừng sinh | Cắt output tại một ký hiệu định sẵn, ví dụ `"###"` |
| `n` | Sinh nhiều câu trả lời cho cùng prompt | So sánh, chọn câu trả lời tốt nhất (tốn tiền gấp n lần) |
| `seed` | Cố gắng cho kết quả lặp lại được | Test, debug, thí nghiệm |
| `presence_penalty` | Phạt token **đã xuất hiện** → khuyến khích nói về chủ đề mới | Brainstorm, tránh lặp ý |
| `frequency_penalty` | Phạt token **xuất hiện nhiều lần** → giảm lặp từ | Văn bản dài bị lặp câu chữ |

## Chọn tham số theo loại tác vụ

| Tác vụ | temperature | max_tokens gợi ý | Ghi chú |
| --- | --- | --- | --- |
| Trích xuất dữ liệu, phân loại, trả JSON | 0 – 0.2 | Vừa đủ cho schema | Cần ổn định tuyệt đối |
| Trả lời câu hỏi dựa trên tài liệu | 0.1 – 0.3 | 500 – 1000 | Bám sát tài liệu, hạn chế bịa |
| Trợ giảng giải thích kiến thức | 0.3 – 0.7 | 500 – 1500 | Cần tự nhiên nhưng chính xác |
| Viết nội dung marketing, brainstorm | 0.8 – 1.2 | Tuỳ độ dài | Cần đa dạng, sáng tạo |

# Token và ước tính chi phí

## Chi phí được tính như thế nào?

Hầu hết nhà cung cấp LLM tính tiền **theo token**, với giá khác nhau cho input và output. Giá thường được niêm yết theo **1 triệu token (1M tokens)**, và **token output đắt hơn token input** (thường gấp 3–5 lần), vì sinh output tốn tài nguyên hơn đọc input.

~~~text
chi_phí = input_tokens  × giá_input_per_1M  / 1_000_000
        + output_tokens × giá_output_per_1M / 1_000_000
~~~

## Ví dụ tính toán

> Giá dưới đây là **giá giả định để minh hoạ**. Giá thật thay đổi thường xuyên, luôn kiểm tra trang pricing của nhà cung cấp trước khi ước tính cho dự án.

Giả sử model có giá **$0.15 / 1M token input** và **$0.60 / 1M token output**. Một lượt chat trợ giảng gồm:

- System prompt: 300 token
- Lịch sử hội thoại: 1.200 token
- Câu hỏi mới: 100 token
- Câu trả lời: 400 token

~~~text
input  = 300 + 1200 + 100 = 1600 token → 1600 × 0.15 / 1_000_000 = $0.00024
output = 400 token                     →  400 × 0.60 / 1_000_000 = $0.00024
tổng một lượt                                                    = $0.00048
~~~

Một lượt rất rẻ, nhưng hãy nhân lên quy mô thật: **500 học viên × 20 câu hỏi/ngày × 30 ngày = 300.000 lượt → khoảng $144/tháng**. Nếu lịch sử hội thoại không được giới hạn và phình lên 10.000 token, chi phí có thể tăng gấp nhiều lần.

## Đếm token trước khi gửi với tiktoken

`usage` trong response cho biết số token **sau khi** gọi. Để ước tính **trước khi** gọi (ví dụ kiểm tra có vượt context window không), dùng `tiktoken`:

~~~python
import tiktoken

def count_tokens(text: str, model: str = "gpt-4o-mini") -> int:
    try:
        enc = tiktoken.encoding_for_model(model)
    except KeyError:
        enc = tiktoken.get_encoding("o200k_base")  # fallback cho model chưa được nhận diện
    return len(enc.encode(text))

print(count_tokens("Hello world"))                 # 2
print(count_tokens("Xin chào các bạn học viên"))   # nhiều hơn số từ
~~~

Đếm token cho một danh sách messages (ước lượng — mỗi message có thêm vài token định dạng):

~~~python
def count_messages_tokens(messages: list[dict], model: str = "gpt-4o-mini") -> int:
    per_message_overhead = 4
    total = 0
    for m in messages:
        total += per_message_overhead + count_tokens(m["content"], model)
    return total + 2
~~~

PRICING = {

# Streaming, lịch sử hội thoại và retry

## Streaming — hiển thị câu trả lời theo thời gian thực

Không có streaming, người dùng phải nhìn màn hình trống cho đến khi model sinh xong toàn bộ câu trả lời — có thể 5–20 giây. Với streaming, API gửi về **từng mảnh (chunk)** ngay khi sinh ra, và chữ xuất hiện dần như đang gõ.

Hai chỉ số độ trễ khi streaming:

- **TTFT (time-to-first-token):** thời gian đến khi chữ đầu tiên xuất hiện — quyết định cảm giác "nhanh" của người dùng
- **Tổng thời gian:** đến khi nhận đủ câu trả lời

~~~python
import time

def stream_chat(messages: list[dict], model: str = "gpt-4o-mini") -> dict:
    start = time.perf_counter()
    first_token_at = None
    parts = []

    stream = client.chat.completions.create(
        model=model,
        messages=messages,
        stream=True,
        stream_options={"include_usage": True},  # nhận usage ở chunk cuối
    )

    usage = None
    for chunk in stream:
        if chunk.usage:
            usage = chunk.usage
        if not chunk.choices:
            continue
        delta = chunk.choices[0].delta.content
        if delta:
            if first_token_at is None:
                first_token_at = time.perf_counter()
            print(delta, end="", flush=True)
            parts.append(delta)

    print()
    return {
        "text": "".join(parts),
        "ttft_s": round(first_token_at - start, 3) if first_token_at else None,
        "total_s": round(time.perf_counter() - start, 3),
        "usage": usage,
    }
~~~

> Khi streaming, `usage` không có sẵn trong từng chunk. Cần bật `stream_options={"include_usage": True}` để nhận số token ở chunk cuối cùng — nếu không sẽ không tính được chi phí.

## Lịch sử hội thoại có giới hạn

Model không nhớ gì giữa các request. Để chatbot "nhớ", ứng dụng phải gửi lại lịch sử. Nhưng nếu gửi **toàn bộ** lịch sử:

- Chi phí input tăng dần theo mỗi lượt
- Đến một lúc sẽ **vượt context window** và request bị lỗi
- Độ trễ tăng

Giải pháp phổ biến nhất: **sliding window** — luôn giữ system prompt, cộng với N lượt gần nhất.

~~~python
class ChatHistory:
    def __init__(self, system_prompt: str, max_turns: int = 10):
        self.system = {"role": "system", "content": system_prompt}
        self.max_turns = max_turns
        self.turns: list[dict] = []

    def add(self, role: str, content: str) -> None:
        self.turns.append({"role": role, "content": content})
        # mỗi lượt gồm 1 message user + 1 message assistant
        overflow = len(self.turns) - self.max_turns * 2
        if overflow > 0:
            self.turns = self.turns[overflow:]

    def messages(self) -> list[dict]:
        return [self.system, *self.turns]
~~~

Các chiến lược nâng cao hơn:

| Chiến lược | Cách làm | Ưu điểm | Nhược điểm |
| --- | --- | --- | --- |
| Theo số lượt | Giữ N lượt gần nhất | Đơn giản | Một lượt dài vẫn có thể vượt giới hạn |
| Theo số token | Bỏ lượt cũ đến khi tổng token < ngưỡng | Kiểm soát chi phí chính xác | Cần đếm token mỗi lượt |
| Tóm tắt | Gọi model tóm tắt các lượt cũ thành một đoạn ngắn | Giữ được ý chính của hội thoại dài | Tốn thêm một lời gọi, có thể mất chi tiết |

> **Lưu ý:** khi cắt lịch sử, không bao giờ cắt mất system prompt, và tránh để lịch sử bắt đầu bằng một message `assistant` lẻ loi không có câu hỏi đi kèm.

## Retry với exponential backoff

API có thể lỗi **tạm thời**: quá nhiều request (429), server quá tải (500, 502, 503), timeout, mất kết nối. Những lỗi này thường tự hết sau vài giây — nên **thử lại**.

Nhưng có những lỗi **không nên thử lại** vì thử bao nhiêu lần cũng sai:

| Nên retry | Không nên retry |
| --- | --- |
| 429 Rate limit | 400 Request sai định dạng |
| 500, 502, 503 lỗi server | 401 Sai API key |
| Timeout, mất kết nối | 403 Không có quyền |
| | 404 Model không tồn tại |

**Exponential backoff:** mỗi lần thử lại, thời gian chờ tăng gấp đôi (1s → 2s → 4s → 8s), cộng thêm một khoảng ngẫu nhiên nhỏ (**jitter**) để nhiều client không cùng thử lại một lúc.

~~~python
import random
import time
from openai import APIConnectionError, APITimeoutError, InternalServerError, RateLimitError

RETRYABLE = (RateLimitError, APITimeoutError, APIConnectionError, InternalServerError)

def with_retry(fn, max_attempts: int = 4, base_delay: float = 1.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except RETRYABLE as e:
            if attempt == max_attempts:
                raise
            delay = base_delay * 2 ** (attempt - 1) + random.uniform(0, 0.5)
            print(f"[retry] lần {attempt} lỗi {type(e).__name__}, chờ {delay:.1f}s")
            time.sleep(delay)

result = with_retry(lambda: call_model("Giải thích exponential backoff trong 2 câu"))
~~~

# Mini-project: trợ lý CLI và nộp bài

## Khung chương trình

~~~python
SYSTEM_PROMPT = (
    "Bạn là trợ giảng của khoá học nền tảng LLM. "
    "Giải thích ngắn gọn, có ví dụ, trả lời bằng tiếng Việt. "
    "Nếu không chắc chắn, hãy nói rõ là không chắc."
)

def main():
    history = ChatHistory(SYSTEM_PROMPT, max_turns=8)
    stats = {"turns": 0, "input_tokens": 0, "output_tokens": 0, "cost": 0.0, "ttft": []}

    print("Trợ lý CLI — gõ /exit để thoát, /reset để xoá lịch sử")
    while True:
        question = input("\nBạn: ").strip()
        if not question:
            continue
        if question == "/exit":
            break
        if question == "/reset":
            history = ChatHistory(SYSTEM_PROMPT, max_turns=8)
            print("Đã xoá lịch sử.")
            continue

        history.add("user", question)
        print("Trợ lý: ", end="")
        result = with_retry(lambda: stream_chat(history.messages()))
        history.add("assistant", result["text"])

        u = result["usage"]
        stats["turns"] += 1
        stats["input_tokens"] += u.prompt_tokens
        stats["output_tokens"] += u.completion_tokens
        stats["cost"] += estimate_cost("gpt-4o-mini", u.prompt_tokens, u.completion_tokens)
        stats["ttft"].append(result["ttft_s"])

    print_summary(stats)

if __name__ == "__main__":
    main()
~~~

1. Model lớn và model nhỏ khác nhau thế nào trên prompt bạn thử (độ trễ, chi phí, chất lượng)?
2. Bạn chọn `temperature` bao nhiêu cho trợ lý CLI và vì sao?
3. Lịch sử hội thoại của bạn giới hạn theo cách nào? Điều gì xảy ra nếu không giới hạn?
4. Lỗi nào nên retry, lỗi nào không? Cho ví dụ.

Tự chấm trước khi nộp:

~~~bash
pytest -q
~~~

## Tiêu chí đánh giá

| Tiêu chí | Tỷ trọng |

## Tổng kết Day01

- LLM sinh văn bản bằng cách **dự đoán từng token**; mọi giới hạn và chi phí đều tính bằng token
- Luôn đọc `finish_reason` và `usage`, không chỉ đọc `content`
- `temperature` thấp cho tác vụ cần chính xác, cao cho tác vụ sáng tạo
- Chi phí = token input × giá input + token output × giá output — và **nhân với quy mô thật**
- Streaming cải thiện trải nghiệm; lịch sử phải có giới hạn; retry chỉ cho lỗi tạm thời
- **Tiếp theo — Day02:** viết prompt tốt để model làm đúng việc ngay từ lần đầu
