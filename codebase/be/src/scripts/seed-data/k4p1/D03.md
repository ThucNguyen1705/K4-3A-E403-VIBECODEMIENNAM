Ngược lại, câu hỏi *"lỗi 429 là gì"* chứa mã lỗi rất cụ thể — ở đây từ khoá lại cực kỳ hiệu quả.

# Embedding là gì?

## Từ văn bản thành vector

**Embedding** là một vector số thực có độ dài cố định (thường vài trăm đến vài nghìn chiều) biểu diễn **ý nghĩa** của một đoạn văn bản. Mô hình embedding được huấn luyện sao cho:

- Các đoạn **gần nghĩa** → vector **nằm gần nhau** trong không gian
- Các đoạn **khác nghĩa** → vector **nằm xa nhau**

~~~text
"Cách cài đặt Python"                  → [ 0.021, -0.113,  0.087, ... ]  (1536 số)
"Hướng dẫn setup môi trường Python"    → [ 0.019, -0.108,  0.091, ... ]  ← rất gần
"Công thức nấu phở bò"                 → [-0.142,  0.056, -0.031, ... ]  ← rất xa
~~~

Mỗi chiều không có ý nghĩa riêng mà con người đọc được (không có "chiều số 7 = độ vui vẻ"). Ý nghĩa nằm ở **vị trí tương đối** giữa các vector.

## Trực giác qua không gian 2 chiều

Hãy tưởng tượng thu nhỏ không gian embedding về 2 chiều:

~~~text
        ▲
        │   • "streaming phản hồi"
        │     • "hiển thị câu trả lời dần dần"
        │
        │                          • "tính chi phí token"
        │                        • "giá mỗi request"
        │
        │  • "cài Python"
        │    • "tạo virtual env"
        └──────────────────────────────────────────►
~~~

Tìm kiếm ngữ nghĩa chính là: **biến câu hỏi thành một điểm, rồi tìm các điểm tài liệu gần nó nhất**.

## Gọi API tạo embedding

~~~python
from openai import OpenAI

client = OpenAI()

resp = client.embeddings.create(
    model="text-embedding-3-small",
    input=[
        "Cách cài đặt Python",
        "Hướng dẫn setup môi trường Python",
        "Công thức nấu phở bò",
    ],
)

vectors = [item.embedding for item in resp.data]
print(len(vectors), len(vectors[0]))   # 3 1536
print(resp.usage.total_tokens)          # embedding cũng tính tiền theo token
~~~

Những điểm cần nhớ:

- **Gửi theo lô (batch):** truyền danh sách nhiều đoạn trong một request nhanh và rẻ hơn gọi từng đoạn
- **Thứ tự được giữ nguyên:** `resp.data[i]` tương ứng với `input[i]`
- **Embedding rẻ hơn nhiều** so với sinh văn bản, nhưng với hàng trăm nghìn đoạn vẫn cần tính toán chi phí
- Mỗi model có **giới hạn độ dài input** — đoạn quá dài cần cắt nhỏ (chunking, Day04)

## Chọn model embedding

| Tiêu chí | Cần cân nhắc |
| --- | --- |
| **Ngôn ngữ** | Dữ liệu tiếng Việt → chọn model đa ngôn ngữ (multilingual) và kiểm tra thực tế |
| **Số chiều** | Nhiều chiều thường chính xác hơn nhưng tốn bộ nhớ và chậm hơn khi tìm kiếm |
| **Chi phí / tự host** | API trả phí hay model mã nguồn mở chạy trên máy chủ riêng |
| **Độ dài input tối đa** | Quyết định kích thước chunk tối đa |

> **Quy tắc bắt buộc:** tài liệu và câu hỏi phải được embedding bằng **cùng một model**. Vector từ hai model khác nhau nằm trong hai không gian khác nhau — so sánh chúng là vô nghĩa. Khi đổi model, phải **embedding lại toàn bộ** tài liệu.

## Ứng dụng của embedding

- **Tìm kiếm ngữ nghĩa** — tìm tài liệu theo ý nghĩa
- **RAG** — cung cấp ngữ cảnh cho LLM (Day04)
- **Gom nhóm (clustering)** — gom câu hỏi của học viên theo chủ đề để biết phần nào khó
- **Phát hiện trùng lặp** — tìm các câu hỏi đã được trả lời trước đó
- **Gợi ý nội dung** — "bài học liên quan"
- **Phân loại** — dùng vector làm đặc trưng cho mô hình phân loại đơn giản

# Đo độ tương đồng giữa hai vector

## Ba cách đo phổ biến

| Độ đo | Công thức | Ý nghĩa | Giá trị |
| --- | --- | --- | --- |
| **Cosine similarity** | `(a · b) / (‖a‖ × ‖b‖)` | Góc giữa hai vector — chỉ quan tâm hướng | -1 đến 1, càng lớn càng giống |
| **Tích vô hướng (dot product)** | `a · b` | Kết hợp cả hướng và độ dài | Không giới hạn |
| **Khoảng cách Euclid** | `‖a − b‖` | Khoảng cách thẳng giữa hai điểm | ≥ 0, càng nhỏ càng giống |

**Cosine similarity** là lựa chọn phổ biến nhất cho embedding văn bản, vì ý nghĩa nằm ở **hướng** của vector chứ không phải độ dài.

## Hiện thực bằng NumPy

~~~python
import numpy as np

def cosine(a, b) -> float:
    a, b = np.asarray(a, dtype=np.float32), np.asarray(b, dtype=np.float32)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

q = embed("Làm sao để câu trả lời hiện ra dần dần?")
d1 = embed("Streaming — hiển thị câu trả lời theo thời gian thực")
d2 = embed("Token và ước tính chi phí")

print(cosine(q, d1))   # ví dụ 0.62 — liên quan
print(cosine(q, d2))   # ví dụ 0.18 — ít liên quan
~~~

## Chuẩn hoá vector — khi cosine bằng tích vô hướng

Nếu mọi vector đã được **chuẩn hoá về độ dài 1** (`‖a‖ = ‖b‖ = 1`), thì:

~~~text
cosine(a, b) = (a · b) / (1 × 1) = a · b
~~~

Nhiều model embedding (trong đó có các model embedding của OpenAI) trả về vector đã chuẩn hoá. Khi đó chỉ cần tính **tích vô hướng** — nhanh hơn vì bỏ được phép tính căn bậc hai. Nếu không chắc, hãy tự chuẩn hoá một lần lúc lưu:

~~~python
def normalize(matrix: np.ndarray) -> np.ndarray:
    norms = np.linalg.norm(matrix, axis=1, keepdims=True)
    return matrix / np.clip(norms, 1e-12, None)
~~~

## Tính cho nhiều tài liệu cùng lúc

Thay vì vòng lặp Python so sánh từng tài liệu, hãy xếp mọi vector tài liệu thành một **ma trận** và tính một lần:

~~~python
doc_matrix = normalize(np.array(doc_vectors, dtype=np.float32))   # shape (N, d)
q = normalize(np.array([query_vector], dtype=np.float32))[0]       # shape (d,)

scores = doc_matrix @ q            # shape (N,) — N điểm tương đồng trong một phép nhân
top_k = np.argsort(-scores)[:3]    # chỉ số 3 tài liệu điểm cao nhất
~~~

Với vài chục nghìn tài liệu, phép tính này chỉ mất vài mili-giây.

## Đọc điểm tương đồng thế nào?

- Điểm **không có ngưỡng tuyệt đối** dùng chung cho mọi model: 0.5 có thể là "rất liên quan" với model này nhưng "bình thường" với model khác.
- Thứ hạng (**ranking**) đáng tin hơn giá trị tuyệt đối.
- Nếu cần ngưỡng để quyết định "không có tài liệu liên quan", hãy **xác định ngưỡng bằng dữ liệu thật**: lấy một bộ câu hỏi có và không có đáp án trong tài liệu, xem phân bố điểm của hai nhóm.

## Lỗi thường gặp

- Quên chuẩn hoá nhưng lại dùng tích vô hướng thay cho cosine → tài liệu dài (vector có độ dài lớn) được ưu tiên sai
- Dùng khoảng cách Euclid nhưng sắp xếp giảm dần như cosine → kết quả ngược
- So sánh vector `float64` và `float32` lẫn lộn, tốn gấp đôi bộ nhớ không cần thiết
- Đặt ngưỡng cứng như 0.8 lấy từ bài viết trên mạng mà không kiểm tra với model của mình

# Xây tìm kiếm ngữ nghĩa từ đầu

## Hai giai đoạn của một hệ thống tìm kiếm

~~~text
GIAI ĐOẠN INDEX (chạy một lần, hoặc khi tài liệu thay đổi)
  Tài liệu → chia đoạn → embedding theo lô → lưu vector + nội dung + metadata

GIAI ĐOẠN QUERY (chạy mỗi khi có câu hỏi)
  Câu hỏi → embedding → so sánh với mọi vector → lấy top-k → trả kết quả
~~~

## Bước 1 — Chuẩn bị dữ liệu

~~~python
from dataclasses import dataclass

@dataclass
class Doc:
    id: str
    lesson: str      # ví dụ "D01"
    title: str       # tên phần bài học
    text: str

docs = [
    Doc("d01-p5", "D01", "Tham số sinh", "temperature điều khiển độ ngẫu nhiên ..."),
    Doc("d01-p7", "D01", "Streaming, lịch sử và retry", "Streaming giúp hiển thị ..."),
    # ...
]
~~~

**Metadata** (lesson, title) không dùng để tính tương đồng, nhưng cực kỳ quan trọng để: hiển thị nguồn, lọc theo bài học, và trích dẫn trong RAG.

## Bước 2 — Embedding theo lô và cache

Embedding lại toàn bộ tài liệu mỗi lần khởi động là lãng phí. Hãy lưu kết quả và chỉ embedding những đoạn **mới hoặc đã thay đổi** — nhận biết bằng hash nội dung.

~~~python
import hashlib
import json
from pathlib import Path

CACHE = Path("embeddings_cache.json")
MODEL = "text-embedding-3-small"

def content_hash(text: str) -> str:
    return hashlib.sha256(f"{MODEL}:{text}".encode()).hexdigest()

def embed_docs(docs: list[Doc], batch_size: int = 100) -> dict[str, list[float]]:
    cache = json.loads(CACHE.read_text()) if CACHE.exists() else {}
    missing = [d for d in docs if content_hash(d.text) not in cache]

    for i in range(0, len(missing), batch_size):
        batch = missing[i : i + batch_size]
        resp = client.embeddings.create(model=MODEL, input=[d.text for d in batch])
        for doc, item in zip(batch, resp.data):
            cache[content_hash(doc.text)] = item.embedding

    CACHE.write_text(json.dumps(cache))
    return {d.id: cache[content_hash(d.text)] for d in docs}
~~~

## Bước 3 — Hàm search

~~~python
import numpy as np

class SemanticIndex:
    def __init__(self, docs: list[Doc]):
        vectors = embed_docs(docs)
        self.docs = docs
        self.matrix = normalize(np.array([vectors[d.id] for d in docs], dtype=np.float32))

    def search(self, query: str, k: int = 3, lesson: str | None = None) -> list[tuple[Doc, float]]:
        q = client.embeddings.create(model=MODEL, input=[query]).data[0].embedding
        q = normalize(np.array([q], dtype=np.float32))[0]
        scores = self.matrix @ q

        if lesson:  # lọc theo metadata
            mask = np.array([d.lesson == lesson for d in self.docs])
            scores = np.where(mask, scores, -np.inf)

        top = np.argsort(-scores)[:k]
        return [(self.docs[i], float(scores[i])) for i in top if np.isfinite(scores[i])]
~~~

Sử dụng:

~~~python
index = SemanticIndex(docs)
for doc, score in index.search("làm sao để chữ hiện ra dần dần", k=3):
    print(f"{score:.3f}  [{doc.lesson}] {doc.title}")
~~~

## Bước 4 — Viết test không cần gọi API

Dùng **embedding giả lập** có kiểm soát để test logic xếp hạng:

~~~python
def test_search_returns_most_similar_first(monkeypatch):
    fake = {
        "streaming": [1.0, 0.0, 0.0],
        "chi phí":   [0.0, 1.0, 0.0],
        "cài đặt":   [0.0, 0.0, 1.0],
    }
    monkeypatch.setattr("search.embed_docs", lambda docs: {d.id: fake[d.text] for d in docs})
    monkeypatch.setattr("search.embed_query", lambda q: [0.9, 0.1, 0.0])

    index = SemanticIndex([Doc("a", "D01", "A", "chi phí"), Doc("b", "D01", "B", "streaming")])
    results = index.search("bất kỳ", k=2)

    assert results[0][0].id == "b"
~~~

> Để test được như trên, hãy tách lời gọi API embedding câu hỏi thành một hàm riêng (`embed_query`) thay vì gọi trực tiếp trong `search`.

## Tiêu chí hoàn thành bài thực hành

- Câu hỏi *"temperature dùng để làm gì"* → top-1 là phần **Tham số sinh**
- Câu hỏi *"làm sao để model trả JSON"* → top-1 là phần **Đầu ra có cấu trúc**
- Câu hỏi *"làm sao để chữ hiện ra dần dần"* (không chứa từ "streaming") → top-3 có phần **Streaming**
- Chạy lại lần hai **không** gọi API embedding cho tài liệu (dùng cache)
- Có test chạy với embedding giả lập

# Vector database và tìm kiếm gần đúng (ANN)

## Khi nào brute-force không còn đủ?

Tìm kiếm ở phần trước là **brute-force (exact search)**: so sánh câu hỏi với **mọi** vector. Độ phức tạp tăng tuyến tính theo số tài liệu.

| Số vector | Bộ nhớ (1536 chiều, float32) | Brute-force |
| --- | --- | --- |
| 10.000 | ~60 MB | Vài mili-giây — hoàn toàn ổn |
| 1.000.000 | ~6 GB | Chậm, tốn RAM |
| 100.000.000 | ~600 GB | Không khả thi trên một máy |

Với khoá học hàng trăm bài học, brute-force bằng NumPy là **đủ tốt**. Vector database trở nên cần thiết khi dữ liệu lớn, cần cập nhật liên tục, cần lọc phức tạp hoặc nhiều dịch vụ cùng truy vấn.

## ANN — Approximate Nearest Neighbor

Thay vì tìm chính xác top-k, **ANN** tìm các vector **gần như** gần nhất, đổi một chút độ chính xác lấy tốc độ nhanh hơn hàng trăm lần.

Chỉ số đánh giá ANN là **recall@k**: trong k kết quả ANN trả về, bao nhiêu phần trăm trùng với k kết quả của brute-force. Các hệ thống thực tế thường đạt recall 95–99%.

## HNSW — thuật toán ANN phổ biến nhất

**HNSW (Hierarchical Navigable Small World)** xây một **đồ thị nhiều tầng**:

- Tầng trên cùng: ít điểm, các cạnh nối xa — dùng để "nhảy" nhanh tới vùng gần đúng
- Tầng dưới cùng: mọi điểm, các cạnh nối gần — dùng để tinh chỉnh

~~~text
Tầng 2:  A ─────────────────────── F
Tầng 1:  A ───── C ────────── E ── F
Tầng 0:  A ─ B ─ C ─ D ─ E ─ F ─ G ─ H
         Tìm kiếm: bắt đầu ở tầng cao, đi tham lam về phía điểm gần câu hỏi nhất,
         xuống tầng thấp hơn và lặp lại.
~~~

Các tham số thường gặp:

| Tham số | Ý nghĩa | Tăng lên thì |
| --- | --- | --- |
| `m` | Số cạnh mỗi điểm | Recall cao hơn, tốn bộ nhớ hơn |
| `ef_construction` | Độ kỹ khi xây chỉ mục | Chỉ mục tốt hơn, build lâu hơn |
| `ef_search` | Độ rộng khi tìm kiếm | Recall cao hơn, truy vấn chậm hơn |

Một họ thuật toán khác là **IVF** (chia không gian thành các cụm, chỉ tìm trong vài cụm gần nhất) — build nhanh, tốn ít bộ nhớ hơn nhưng thường recall thấp hơn HNSW ở cùng tốc độ.

## Các lựa chọn phổ biến

| Công cụ | Kiểu | Phù hợp khi |
| --- | --- | --- |
| **pgvector** | Extension của PostgreSQL | Đã dùng Postgres, muốn vector nằm cùng dữ liệu nghiệp vụ, lọc bằng SQL |
| **Chroma** | Thư viện nhúng / server nhẹ | Prototype nhanh, chạy local |
| **FAISS** | Thư viện (không phải database) | Tìm kiếm trong bộ nhớ, tốc độ cao, tự quản lý lưu trữ |
| **Qdrant / Weaviate / Milvus** | Server chuyên dụng | Dữ liệu lớn, cần scale, lọc metadata mạnh |

## Ví dụ với pgvector

VLearn đang dùng PostgreSQL, nên pgvector là lựa chọn tự nhiên — không phải vận hành thêm hệ thống mới.

~~~sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE lesson_chunks (
  id          BIGSERIAL PRIMARY KEY,
  lesson_id   UUID NOT NULL,
  part_title  TEXT NOT NULL,
  content     TEXT NOT NULL,
  embedding   vector(1536) NOT NULL
);

-- Chỉ mục HNSW cho khoảng cách cosine
CREATE INDEX ON lesson_chunks USING hnsw (embedding vector_cosine_ops);

-- Tìm 5 đoạn gần nhất trong một bài học
-- Toán tử <=> trả về KHOẢNG CÁCH cosine (= 1 - cosine similarity), càng nhỏ càng giống
SELECT part_title, content, 1 - (embedding <=> $1) AS similarity
FROM lesson_chunks
WHERE lesson_id = $2
ORDER BY embedding <=> $1
LIMIT 5;
~~~

Ghi nhớ các toán tử của pgvector:

| Toán tử | Ý nghĩa |
| --- | --- |
| `<->` | Khoảng cách Euclid (L2) |
| `<=>` | Khoảng cách cosine |
| `<#>` | Tích vô hướng **âm** (để sắp xếp tăng dần) |

## Hybrid search — kết hợp từ khoá và ngữ nghĩa

Như đã thấy ở phần tổng quan, mỗi cách tìm kiếm mạnh ở một kiểu câu hỏi. **Hybrid search** chạy cả hai và **gộp thứ hạng**. Cách gộp đơn giản và hiệu quả là **Reciprocal Rank Fusion (RRF)**:

~~~python
def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

final = rrf([keyword_results, semantic_results])
~~~

RRF chỉ dùng **thứ hạng**, không dùng điểm số, nên không cần lo điểm của hai phương pháp nằm trên thang đo khác nhau.

# Tổng kết Day03 và câu hỏi ôn tập

## Những ý chính cần nhớ

- **Embedding** biểu diễn ý nghĩa văn bản bằng vector; văn bản gần nghĩa → vector gần nhau
- Tài liệu và câu hỏi **bắt buộc** dùng cùng một model embedding; đổi model phải embedding lại toàn bộ
- **Cosine similarity** là độ đo phổ biến; với vector đã chuẩn hoá, cosine = tích vô hướng
- Thứ hạng đáng tin hơn giá trị điểm tuyệt đối; ngưỡng phải xác định bằng dữ liệu thật
- Hệ thống tìm kiếm gồm hai giai đoạn: **index** (một lần) và **query** (mỗi câu hỏi)
- **Cache embedding** theo hash nội dung để không trả tiền embedding lại
- Brute-force đủ tốt cho dữ liệu nhỏ; dữ liệu lớn cần **ANN** (HNSW) và vector database
- **Hybrid search** kết hợp điểm mạnh của từ khoá và ngữ nghĩa; RRF là cách gộp đơn giản

## Lỗi thường gặp khi làm tìm kiếm ngữ nghĩa

| Lỗi | Hậu quả | Cách khắc phục |
| --- | --- | --- |
| Embedding cả tài liệu dài thành một vector | Ý nghĩa bị "loãng", tìm kiếm kém chính xác | Chia thành đoạn nhỏ (chunking — Day04) |
| Không lưu metadata | Không biết kết quả đến từ bài nào, không trích dẫn được | Lưu id, bài học, tiêu đề cùng vector |
| Đổi model embedding nhưng giữ vector cũ | Kết quả tìm kiếm vô nghĩa | Đưa tên model vào khoá cache, embedding lại |
| Không có bộ câu hỏi kiểm thử | Không biết thay đổi làm tốt lên hay tệ đi | Chuẩn bị 20–30 câu hỏi có đáp án tài liệu đúng |
| Dùng vector database quá sớm | Thêm độ phức tạp vận hành không cần thiết | Bắt đầu bằng NumPy hoặc pgvector |
